SquashSense — project overview

STUDENT-BUILT TRAINING RESEARCH PROTOTYPE · LEON · UPDATED OCTOBER 2026

SquashSense is a prototype that records a squash swing from two sides at once: a small motion sensor on the end of the racket grip, and a camera on a courtside computer that tracks the player's body. The software puts both on one timeline so a swing can be reviewed with numbers and video together after a session. It was built by Leon, a high-school squash player, out of personal interest. It is not a product and nobody can currently try it.

What it consists of

  • Racket sensor — an ESP32-S3 microcontroller board with an ICM42688 six-axis IMU (three-axis accelerometer and three-axis gyroscope) in a short cylindrical housing fixed to the butt end of the grip. Configured at 500 samples per second; the receiving software counted about 504 Hz in the recorded session. Data goes by ESP-NOW (a short-range Wi-Fi-based protocol) to a USB receiver on the courtside computer.
  • Body tracking — a camera connected to the courtside computer; Google's MediaPipe Pose model finds 33 landmarks per frame, and SquashSense's own code computes joint-angle labels, a wrist path and swing phases from them. 14–16 frames per second in the recorded session.
  • Courtside computer — a Radxa ROCK 5C single-board computer in an enclosure held to the court glass by a suction mount. It runs the pose model, receives the sensor stream, detects swings, aligns the clocks and serves the web interface over the local network.

What has been demonstrated

One session was recorded in full: 27 August 2026, free hitting, 22 minutes, one player (Leon), 197 swings detected by the software. The screen recording shows the whole pipeline running live on court: sensor → wireless → computer → browser chart; camera → landmarks → angle labels; swing detection and phase assignment on real swings; and a session report generated at the end. A small number of other informal court sessions took place but were not logged, so no count is quoted.

What is reported but not independently verified

The following come from Leon's recorded introduction (12:32, in English) and earlier notes. The application and firmware code were not inspected for this overview.

  • Swing detection looks for sustained acceleration rather than a fixed speed threshold (an earlier threshold version missed slow, compact swings); contact is marked when a shock appears on the accelerometer while the racket is near peak speed; phases are assigned afterwards from direction changes.
  • Clocks are aligned on the fastest observed packet delivery, corrected gradually as they drift, with the remaining uncertainty displayed.
  • Detection and scoring were developed on a simulator before the court sessions.

What has not been done

  • No reference method (radar, motion capture, labelled video); no accuracy figure for any metric.
  • No measurement of the timing error between a video frame and the sensor peak.
  • No measurement of sensor weight, size, battery life, setup time, or effect on racket balance.
  • No evidence that using the interface changes how anyone plays.

Next steps (Leon's plan)

  • Record and label real sessions swing by swing; tune detection and scoring on that data instead of the simulator.
  • Calibrate the sensor's mounting orientation to separate forehand from backhand.
  • Add video tracking of the racket and ball to get the real racket-head path and contact point, and compare them with the sensor's estimates.
  • A small multi-week comparison of players with and without the interface.

Who did what

Leon assembled the hardware, wrote the sensor firmware (IMU reading, a packet format with corruption detection, the wireless link), the sensor-data processing, the clock alignment, the swing detector and phase logic, and the training interface, and ran the court tests. Body landmarks come from Google's MediaPipe Pose; wireless uses Espressif's ESP-NOW; the interface uses open-source web libraries; all hardware is off-the-shelf. Teammates took part in court tests, a teacher advised, and parts of the code were written with AI coding assistants with Leon doing the debugging and iteration.
